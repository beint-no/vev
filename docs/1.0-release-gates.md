# Vev 1.0 release scope and evidence

Vev 1.0.0 is the first stable release of the documented native persistence API.
The release scope was narrowed on September 7, 2026 to finish and publish the
implemented library, with full ReAI replacement continuing as follow-up work.
Earlier plans required complete replacement before 1.0; that milestone is now
separate. A stable version does not prove complete Hibernate compatibility,
Jakarta provider conformance, or a general performance advantage.

| Area | 1.0 evidence and boundary |
|---|---|
| JDK | JDK 27 baseline; verified on OpenJDK RC `27+35-2325`. Final-distribution verification remains pending. No preview API is required by the native Vev modules. |
| Mapping compiler | Source and separately compiled Java/Kotlin immutable records; bounded scalar, enum, binary and text values; explicit capabilities; positive and negative compiler fixtures. Unsupported associations, composite entity keys, and value shapes remain rejected. |
| Reads | Point/batch reads, bounded equality/null pages, typed ASC/DESC value/ID cursors, explicit SELECT-only and shared records. Joins, projections, aggregates, arbitrary predicates and pessimistic locking remain future work. |
| Writes | Assigned insert, generated integer identity creation, optimistic update, opt-in versioned generated-identity deletion, and atomic bounded batches. No implicit cascade graph, dirty checking or arbitrary upsert. |
| Schema | Generated manifests, live catalog/privilege attestation, exact keys/indexes/checks/defaults, historical missing-value storage, closed entity references and explicit external tenant-registry foreign keys. Migrations remain application-owned. |
| Isolation/failures | Synthetic PostgreSQL fixtures exercise tenant boundaries, rollback-only propagation, stale/serialization/timeout/cancellation failures, connection ownership, cleanup and ambiguous commits. These are library tests, not complete application workflow evidence. |
| ReAI | Activity catalogue and timesheet Activity reference reads migrated in the application PR. Full application build/startup, catalogue and weekly-summary parity, request/job scopes, caller rollback and recovery verified in a marked private clone. Other entities and every application write still use Hibernate. |
| Performance | Published synthetic allocation observations remain narrowly scoped; prior latency evidence was rejected. No claim of outperforming Hibernate or being the fastest JVM ORM. Representative stable-Hibernate comparisons remain pending. |
| Distribution | Versioned Maven repository archive, matching processor/runtime, ABI 7, source/Javadoc artifacts, deterministic archives and isolated published-consumer verification. See the release procedure. |
| Operations | ReAI PR and local migration/rollback evidence exist. Production image, role provisioning, rollout, restored-data workflows, and complete Hibernate removal remain pending. No application deployment is part of this release. |

Final library verification: **373 tests, zero failures, errors or skipped tests**,
plus the isolated published consumer and Javadoc with warnings treated as errors.
The release bundle is rebuilt for byte-for-byte comparison before publication.

## Next steps

1. Verify the final JDK 27 distribution and production container, keeping Java/Kotlin
   compilation and preview use explicit.
2. Complete ReAI migration aggregate by aggregate. Start with typed projections and
   query predicates, creation/update input semantics, and explicit transaction
   integration needed for an atomic real write workflow. Preserve every business
   constraint and compare accounting, payment, inventory, and scheduled workflows.
3. Measure latency, throughput, allocation, startup, build cost, and query counts
   against ReAI's stable Hibernate version on an isolated, monitored machine.
   Optimize demonstrated bottlenecks without weakening correctness.
4. Improve migration tooling and diagnostics, add tenant-bound opaque cursors,
   dependency/API compatibility automation, and repeatable release verification.
5. Track final Jakarta Persistence 4. Adopt compatible additions only where they
   preserve immutable records, compile-time safety and efficient execution; keep
   provider-conformance claims separate from annotation reuse.

Public fixtures are synthetic. Private application code, schema inventories,
customer data and local verification reports are not release assets.
