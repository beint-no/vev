# Vev 1.0 release gates

The release objective is a verified Hibernate replacement in ReAI, with JDK 27 as
the execution baseline and ahead-of-time mapping/query compilation. Jakarta
Persistence 4 compatibility is evaluated operation by operation; it must preserve
compile-time safety and measured performance. Reusing annotation names is not
provider conformance. A version bump or successful synthetic suite does not satisfy
the application replacement gate.

No 1.0 tag or artifact may be published while a required gate is unresolved.
The experimental notice stays until the gates below have evidence at the intended
release commit. Private application source, database rows, and application-specific
reports stay in the application repository; public fixtures remain synthetic.

| Gate | Required evidence | Current state |
|---|---|---|
| JDK 27 | Clean verification, published-consumer build, actual application startup, cancellation and ownership checks on the final JDK distribution | Vev passes on OpenJDK RC `27+35-2325`; final distribution verification pending |
| Source model | Every application mapping is either compiled exactly or explicitly migrated with equivalent behavior | Source and separately compiled Java/Kotlin records plus bounded scalar/enum/binary mappings implemented; application model migration, associations, composite keys, and several value representations pending |
| Queries | Inventory all repositories and declared/dynamic queries; compile their plans; verify result values, nulls, ordering, pagination, projections, joins, aggregates, and locking | Point/batch reads and bounded scalar/enum equality pages implemented; application query coverage pending |
| Writes | Verify all write paths, generated IDs, explicit update/delete semantics, relationship changes, constraints, optimistic conflicts, and transaction propagation | Assigned-ID insert, typed integer identity creation, and versioned update implemented; application write migration pending |
| Schema | Preserve business constraints and tenant-composite foreign keys; compare generated expectations with migrated PostgreSQL; verify least-privilege access | Generated manifest, live attestation, tenant-composite scalar foreign keys, and named tenant-scoped unique constraints implemented; integer identities, owned sequences, declared primary-key shapes, tenant traversal indexes, and alternate reference keys implemented; declared checks, approved expression dependencies, and required binary length constraints implemented; application schema acceptance pending |
| Tenant isolation | Adversarial tests through application request, job, repository, and transaction boundaries, including intentionally cross-tenant identifiers | Kernel isolation tested; complete application migration pending |
| Failure behavior | Cancellation, timeout, serialization, deadlock, stale updates, rollback-only propagation, pool reuse, resource cleanup, and ambiguous commit handling | Kernel failure fixtures exist; application failure/recovery evidence pending |
| Application replacement | Build and start the whole application; exercise representative accounting, payment, inventory, and scheduled workflows against disposable restored data; verify Hibernate is absent from the replacement runtime graph | Pending; a preparatory application build is not replacement evidence |
| Performance | Reproducible comparable workloads against the Hibernate version used by the application, with realistic data shapes; report latency, throughput, allocation, startup, build cost, and query counts | Earlier synthetic latency evidence is rejected; representative replacement evidence pending |
| Operations | Reviewed application PR, migration and rollback procedure, container baseline, health/log verification, documented supported upgrade/recovery paths | Pending |
| Public contract | Reviewed API and compatibility matrix, deterministic artifacts, dependency/license review, versioned migration contract, reproducible release procedure | In progress; no stable release published |

Preview APIs may be adopted where they simplify ownership or failure behavior or
produce a measured improvement. Their use requires exact JDK build documentation
and re-verification when the preview contract changes. Preview adoption itself is
not a performance result.

The application can be migrated in explicit steps, but 1.0 requires complete
replacement evidence. Do not remove database constraints or silently drop ORM
semantics to make a mapping compile. Expand the generated contract or implement
and verify the corresponding application change first.
