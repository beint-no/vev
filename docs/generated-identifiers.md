# PostgreSQL identity creation

An immutable persisted snapshot always has a non-null identifier. Declare an
explicit `@GeneratedValue(strategy = GenerationType.IDENTITY)` on a scalar
`@Id` of type `short`, `int`, `long`, `Short`, `Integer`, or `Long` to let
PostgreSQL allocate it. `AUTO`, `SEQUENCE`, `TABLE`, `UUID`, named generators,
nullable identifiers, arbitrary defaults, and legacy `serial` columns are rejected.

```java
@Entity
@Table(name = "entry", schema = "ledger")
public record Entry(
        @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
        @Column(name = "id", nullable = false) Long id,
        @TenantKey @Column(name = "tenant_id", nullable = false) Integer tenantId,
        @Version @Column(name = "version", nullable = false) Long version,
        @Column(name = "description", nullable = false, length = 128) String description,
        @Column(name = "reference", nullable = true, length = 64) String reference) {
}
```

The processor generates `EntryVev.New(String description, String reference)`.
This separate record contains only VALUE components, in their declaration order.
It cannot carry an assigned ID, tenant, or version. A record with no VALUE fields
has an empty creation record. Kotlin `@JvmRecord` dependencies use the same
contract, with their normal null assertions retained when persisted snapshots
are constructed.

```java
Entry entry = vev.write(tenant, tx -> tx.entities().create(
        EntryVev.INSTANCE, new EntryVev.New("Created explicitly", null)));

Batch<Entry> entries = vev.write(tenant, tx -> tx.entities().createMultiple(
        EntryVev.INSTANCE,
        Batch.copyOf(List.of(new EntryVev.New("First", null), new EntryVev.New("Second", null)))));
```

Creation supplies the lexical tenant and initializes a mutable snapshot's version
to zero. `@AppendOnly` identity snapshots have no version. The returned snapshot
supports the usual typed reads and, when versioned, explicit updates. Neither
creation method mutates the input. Each row is checked against its input values,
allocated ID, tenant, and initial version before it is returned.

Assigned-ID `insert` and `insertMultiple` require `AssignedEntityType`; identity
plans instead expose `GeneratedEntityType`. Mixing these capabilities, supplying
a persisted snapshot as a creation input, or supplying another model's input
fails Java compilation. The nonconforming Jakarta `EntityAgent` facade rejects
identity insertion before SQL: its `void` API cannot return an immutable replacement
snapshot carrying the new ID. Applications must capture the native API's result.

## Database contract

The live table must retain the complete generated schema contract, including the
current `(tenant, id)` primary key, forced RLS, exact business constraints, and
column privileges. Support for identity allocation does **not** yet admit a table
whose primary key is only `(id)`. Do not remove existing business constraints or
change application IDs merely to satisfy the current schema profile.

Both PostgreSQL `GENERATED ALWAYS AS IDENTITY` and `GENERATED BY DEFAULT AS IDENTITY`
are accepted. Vev verifies the identity column's internally owned sequence, exact
integer width, permanent logged storage, matching schema and table owner, start
and minimum one, increment one, the integer type's maximum, positive cache size,
and no cycling. The application role must have effective sequence `USAGE` and no
`SELECT`, `UPDATE`, or grant option. Sequence privileges are additional to the
existing column-level `INSERT` grants, including the ID column.

For example, the table above needs `id bigint GENERATED ALWAYS AS IDENTITY` and
`PRIMARY KEY (tenant_id, id)`. Its migration must grant `USAGE` on the internally
owned identity sequence. Vev discovers and verifies that sequence from catalog
dependencies; it never guesses the sequence name. The generated schema manifest
records the identity and privilege contract, and identity allocation changes the
model fingerprint.

## Batch correlation and failure behavior

`createMultiple` accepts up to 1,000 inputs. It validates every application value
before SQL and executes one set-based statement using bound typed arrays. Empty
batches perform no creation SQL. `create` currently uses the same statement path
for one input.

A materialized input relation allocates an ID for each input ordinal with
`pg_catalog.nextval`. Insertion uses `OVERRIDING SYSTEM VALUE`, and a join on the
allocated ID and tenant correlates each returned row with its exact input ordinal.
Repeated or null payload values are unambiguous; the implementation does not
assume an ordering for PostgreSQL's `RETURNING` rows. Arrays are expanded with
`unnest`, including exact cardinality guards, rather than indexed repeatedly.
The sequence OID is bound as a `regclass` parameter and stored in the verified
runtime, never in a shared generated model or caller-supplied SQL.

A unique-key failure, invalid reference, exhausted sequence, unexpected returned
row, or JDBC cleanup failure poisons and rolls back the **whole lexical
transaction**, including earlier successful statements. Catching that exception
inside the callback cannot permit a partial commit. A rejected application value
before SQL follows the existing recoverable validation contract.

IDs can contain gaps and do not represent commit order. Rollback and caching can
consume values without committed rows. Identity numbers must not serve as gapless
invoice or other business numbering. Their shared progression can disclose
aggregate allocation activity across tenants; RLS protects row access, not this
side channel. Use assigned opaque identifiers when that observation is unacceptable.
Applications must never reset or reuse committed identifiers. Migration, sequence
replacement, restart, or endpoint changes require a newly verified runtime.

PostgreSQL documents [identity-column behavior](https://www.postgresql.org/docs/18/ddl-identity-columns.html),
[explicit identity overrides](https://www.postgresql.org/docs/18/sql-insert.html),
and [atomic allocation and rollback gaps](https://www.postgresql.org/docs/18/functions-sequence.html).

## Evidence and remaining work

Processor coverage exercises all six Java identifier representations, source and
binary equivalence, deterministic manifests, adjacent unsupported generators,
and incompatible insertion capabilities. PostgreSQL fixtures exercise both identity
modes, all three widths, Kotlin nullability, duplicate payloads, empty inputs,
1,000-row batches, concurrent tenant batches, explicit updates, business-constraint
rollback, exhaustion, sequence privilege/shape rejection, altered returned rows,
and array cleanup failures.

These are correctness and statement-count checks. Historical read/update JMH
results do not measure this new creation path and establish no identity-insert
performance claim. Single-column primary keys, more schema shapes, application
workflow parity, and representative performance evidence remain release work.
